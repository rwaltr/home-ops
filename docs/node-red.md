# Node-RED

Low-code flow automation, replacing Windmill. One container, no database.

| Piece    | Value                                                                  |
| -------- | ---------------------------------------------------------------------- |
| Web UI   | `https://nodered.waltr.tech` (envoy-internal **only** — not published) |
| Image    | `docker.io/nodered/node-red:5.0.10` (multi-arch index digest pinned)   |
| Chart    | shared `app-template` `5.2.1`                                          |
| Port     | 1880                                                                   |
| State    | PVC `node-red-data` (2Gi, openebs-hostpath) → `/data`                  |
| Settings | ConfigMap `node-red-settings` → `/data/settings.js` (subPath)          |
| Secret   | `node-red-credential-secret`, generated in-cluster                     |
| Backup   | kopiur component, `H 18 * * *`                                         |

Manifests: `infra/k8s/kyz/apps/default/node-red/{ks.yaml,app/}`.

## Why the official image

It runs as uid 1000, keeps its user dir in `/data`, and **ships git and
OpenSSH**. Projects need git, and a custom image would be one more thing to
rebuild on every bump. The root filesystem stays read-only: `HOME` points at
`/data`, so the npm and git caches that Projects write land on the volume.

## Where the flows live

**Not in this repo.** This was Windmill's problem: a CLI sync wrote workflow
files into `home-ops`. Node-RED's Projects feature keeps each flow set in its own
git repository, so `home-ops` holds only the deployment.

Setup, once:

1. Create an empty repository on Forgejo, for example `rwaltr/node-red-flows`.
   Keep it private: flows contain API endpoints and credential references.
2. Open `https://nodered.waltr.tech`, then **Projects → Create project**.
3. Give it a name, and let Node-RED migrate its empty default flow into it.
4. Set the git user name and email when prompted.
5. Add the remote: **Project settings → Git remotes**, URL
   `ssh://git@git.waltr.tech/rwaltr/node-red-flows.git`.
6. Generate an SSH key in the editor (**Project settings → SSH keys**), add the
   public half to the Forgejo repo as a deploy key with write access.
7. Commit, then push.

The key and the git checkout live under `/data`, which is backed up. The
credential secret is the exception, below.

## The credential secret

Flow credentials — the Paperless token, the Immich API key — are encrypted with
`NODERED_CREDENTIAL_SECRET` before they reach `flows_cred.json`. The value is
generated by the `Password` generator and injected by the ExternalSecret beside
it, so it is never in git.

`refreshInterval: "0"` on that ExternalSecret is load-bearing. A Password
generator mints a new value on every sync, and a rotated credential secret makes
every credential already stored in the flows undecryptable. Deleting the Secret
mints a new one and orphans them, so re-enter them in the editor if that happens.

A restore needs both the PVC and this Secret. With only the PVC, the flows open
but their credentials read as invalid.

## Kanidm access control

Envoy Gateway enforces OIDC on `HTTPRoute/node-red` with the route-scoped
`SecurityPolicy/node-red-oidc`. The Kanidm client and the policy live next to the
app manifests. The callback is
`https://nodered.waltr.tech/oauth2/callback`, and the policy uses the issuer
`https://idm.waltr.tech/oauth2/openid/node-red`.

Kanidm mints the client ID and secret into the `default` namespace Secret
`node-red-kanidm-oauth2-credentials`. Envoy reads the `client-id` and
`client-secret` keys directly. It sends PKCE, which meets kaniop's default
requirement. Users must belong to `idm_all_persons` and have a primary mail
attribute for the requested email scope.

The `NetworkPolicy/node-red-ingress` allows port 1880 only from Envoy pods in the
`network` namespace. This matters because direct Service access would bypass the
Gateway's OIDC policy. Node-RED does not duplicate authentication with `adminAuth`.

Gatus accepts either 302 from the OIDC redirect or 200 if its client follows the
redirect. The pod probes use TCP and do not pass through Envoy.

Verify the route gate after Flux applies the changes:

```sh
curl -sSI https://nodered.waltr.tech/ | head -10
kubectl -n default get securitypolicy node-red-oidc
kubectl -n default get networkpolicy node-red-ingress
kubectl -n default get kanidmoauth2client node-red
```

The browser should redirect to Kanidm. The OAuth client must become ready before
the Gateway can complete the login flow.

## Rebuilding the pipelines

Both Paperless pipelines are unbuilt after the Windmill removal. Rebuild them as
flows rather than scripts:

- **Poll** with an Inject node on a 5-minute interval, or a Cron node.
- **HTTP Request** nodes for `GET /api/assets`, `POST /api/documents/post_document/`
  and the `intel-vl` chat call through `agentgateway`.
- **Function** nodes in JavaScript for the verdict logic.
- **Switch** nodes on the model's verdict.

Keep the Immich tags (`document`, `useless`, `paperless-sent`) as the idempotency
state. They already mean what the old bridge meant, and they survive a rebuild.

## Verification

```sh
kubectl -n default get hr,pvc,httproute | grep node-red
kubectl -n default logs deploy/node-red -c app --tail=20
kubectl -n default get externalsecret node-red-credential-secret   # SecretSynced
```

The boot log is the check that matters, because both settings are load-bearing:

```text
[info] Settings file  : /data/settings.js
[info] User directory : /data
```

`Projects disabled` appearing instead means the ConfigMap did not mount, or the
`editorTheme.projects.enabled` block is missing. A missing
`NODERED_CREDENTIAL_SECRET` shows up the first time a flow saves a credential,
not at boot.

The route is internal only, so `curl` from the LAN hits the internal gateway
directly. Nothing about this hostname resolves publicly: there is no
`envoy-external` parentRef, and `external-dns` publishes only that gateway.
